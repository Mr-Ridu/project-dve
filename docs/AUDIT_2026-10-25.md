# Security & privacy audit — 25 October 2026

Scope: the whole Django site, with extra depth on the tutorial library (catalog,
access control, playback, progress) and on what visitors' browsers are exposed
to. Reviewed by reading the code and by running proofs-of-concept against a live
instance of the app; every finding below states which of the two it rests on.

Nothing was changed by this audit.

---

## 1. Summary

| ID | Severity | Finding |
|---|---|---|
| H1 | High | Playback redeem token is not bound to a session — an anonymous client can replay a captured token and receive a signed video URL (reproduced) |
| H2 | High | A Facebook-pixel script (with `eval` of a remote response) still executes on 51 of the 56 mirrored pages (reproduced) |
| M1 | Medium | YouTube/Vimeo iframes on 13 mirrored pages send visitor IP + cookies to third parties, with no consent |
| M2 | Medium | No Content-Security-Policy on any page, while mirrored pages carry dozens of inline scripts |
| M3 | Medium | Login/registration throttling is per (IP + username) — no per-IP or per-account ceiling, so credential stuffing is unbounded |
| M4 | Medium | `/admin/login/` has no throttling at all and bypasses the app's login counter |
| M5 | Medium | The published privacy and cookie policies are the mirrored originals (97 references to "Xstrahl", no retention terms, wrong controller) |
| M6 | Medium | No data-subject tooling and no retention: audit events keep IP + identity indefinitely; no export or account deletion |
| M7 | Medium | Progress endpoint has no rate limit — completion can be forged by hammering it |
| L1 | Low | `handler500` points at the 404 view: real server errors return 404 "Page not found", hiding incidents from monitoring |
| L2 | Low | No password-reset flow; a locked-out user needs a staff member with admin access |
| L3 | Low | Mirrored pages still ship the old WordPress JS bundles (including an `eval` in a bundled library) |
| L4 | Low | `/media/` is served only while `DEBUG=True`, so tutorial thumbnails will 404 in production |

None of the findings allow reading another user's personal data. H1 and H2 are
the two that should be fixed before the library is opened to real customers.

## 2. Tutorial security — what holds

Verified by reading `tutorials/access.py`, `tutorials/views.py` and the tests:

- **One predicate, re-evaluated per request.** `can_access()` = authenticated +
  active + approved + published + (all-library flag or explicit grant). It is
  called on the catalog, the detail page, playback authorization *and* progress
  reporting. Revoking a grant denies the very next request (test:
  `test_revocation_between_authorize_and_redeem_wins`).
- **Progress is never authorization.** `TutorialProgress` is not consulted
  anywhere in the access path.
- **Unpublished = 404 for everyone**, grants included — no existence leak.
- **Playback is two-stage and CSRF-protected.** `authorize` mints a 32-byte
  opaque token (5 min, one-time), `redeem` re-checks access and only then signs
  the Bunny embed (1 h TTL). Both are POST-only.
- **`video_ref` never reaches the browser.** No template references it; a test
  asserts the signing key never appears in the redeem response.
- **Staff surface is gated and audited.** Every dashboard view requires
  active + staff; self-approval is blocked; every mutation writes an
  `AuditEvent` with the actor and the direct socket IP (not `X-Forwarded-For`).
- **Uploads are constrained.** Thumbnails are staff-only, limited to
  png/jpg/jpeg/webp/gif (no SVG) and 5 MB.
- **Denied tutorial pages** show a generic "Tutorial unavailable" without the
  tutorial's content.

## 3. Findings

### H1 — Playback token can be replayed by anyone (High)

**Where:** `tutorials/views.py` — `playback_authorize` stores
`{user_id, tutorial_id}` under a random key; `playback_redeem` looks the key up
and authorizes the *cached* user, never comparing it with `request.user`.

**Reproduced:**

```
alice POST /tutorials/<slug>/authorize/   → 201 {token}
anonymous POST /tutorials/redeem/ {token} → 200 {provider, embed_url}
```

**Impact:** the token is a bearer credential for playback. Anyone who obtains it
within its 5-minute life — from a log, a shared screen, a browser extension, a
referrer leak, or any future XSS — can pull a signed embed URL without an
account, and can then share that 1-hour embed URL onwards.

**Fix (small):** bind the token to the requesting session (`request.session
.session_key`) and reject the redeem when it does not match; alternatively
require `request.user.is_authenticated` and equality with the cached user id.
Also consider binding to the client IP. Add a test that replays a token from a
second client and expects 403.

### H2 — Facebook pixel script still runs on mirrored pages (High)

**Where:** `core/sanitize.py`, `_BAD_SCRIPT` pattern.

**Reproduced** on `/benign-conditions/` (and most other `/legacy/` pages):

```html
<script type='text/javascript'>
  document.addEventListener('wpcf7mailsent', function (event) {
    if ("fb_pxl_code" in event.detail.apiResponse) {
      eval(event.detail.apiResponse.fb_pxl_code);
    }
  });
</script>
```

The block matches none of the current patterns (`FacebookSignal`,
`runPixelCode`, `Meta Pixel`, `gtag(` …), so it survives. Two problems at once:
a tracker that contradicts the site's "no third-party trackers" promise, and an
`eval()` of a network response — a script-injection sink that CSP would not
help with.

**Fix (small):** extend `_BAD_SCRIPT` with `fb_pxl_code`, `eval(event.detail`,
`wpcf7mailsent`; add a sanitizer test that scans every legacy file for `eval(`,
`fb_pxl_code` and `apiResponse`. The double `</script> </script>` left in the
output suggests the block-splitting logic also needs a regression test.

### M1 — Third-party media on mirrored pages (Medium)

13 pages embed YouTube or Vimeo (`xstrahl-100`…`xstrahl-300`, `sarrp`,
`sarrp-beamline`, `sarrp-flash`, `radiant`, `skin-cancer`, `benign-conditions`,
`for-patients`, `nmsc-webcast`, `smart-rad-overview`). Loading those pages contacts Google/Vimeo and sets their
cookies before any consent, and the visitor's IP is disclosed. Options: replace
with a click-to-load poster that only injects the iframe on interaction (keeps
the video, removes the passive transfer), or convert the pages to the new design
and host the clips on Bunny.

### M2 — No Content-Security-Policy (Medium)

Response headers today: `X-Frame-Options: DENY`, `Referrer-Policy:
same-origin`, `X-Content-Type-Options: nosniff`,
`Cross-Origin-Opener-Policy: same-origin` — no CSP. The new templates are
clean, but legacy pages contain dozens of inline `<script>` blocks, so a
`script-src` policy needs `'unsafe-inline'` today (or nonce-rewriting in the
sanitizer). A starting point that costs nothing: `default-src 'self'; img-src
'self' data: https://*.b-cdn.net; frame-src https://player.mediadelivery.net;
object-src 'none'; base-uri 'self'; form-action 'self'`.

### M3 — Throttling counts only (IP + username) (Medium)

`accounts/throttle.py` keys on both, so an attacker from one IP can try 5
passwords each against unlimited usernames. Add a per-IP counter (e.g. 30
failures/5 min across all usernames) and keep the per-account counter. The
current `LocMem` cache is per-process in development; production uses the DB
cache, which is correct.

### M4 — Django admin login is unthrottled (Medium)

`/admin/login/` is Django's own view. A staff username can be brute-forced there
without ever touching the app's counter. Either throttle at the web-server level
for `/admin/`, restrict `/admin/` by IP, or add a small middleware that applies
the same counter to `django.contrib.auth.views.LoginView` posts.

### M5 — Privacy and cookie policies are the wrong company's (Medium)

`/privacy-policy/` and `/cookie-policy/` are still the mirrored pages from the
original site: 97 and 54 mentions of "Xstrahl" respectively, one mention of
Techno Mate, no retention periods, and Facebook references that no longer match
the site's behaviour. These are the pages a regulator or a hospital procurement
team reads first. They need rewriting for Techno Mate (controller, purposes,
processors: Bunny Stream, hosting, email; retention; rights; cookies actually
set).

### M6 — No retention and no data-subject tooling (Medium)

`AuditEvent` keeps actor, target, action, detail and IP forever; nothing purges
it. There is no export and no self-service deletion, and deleting a user cascades
grants/progress but the audit rows keep `target_user = NULL` with the IP intact.
Minimum viable: a documented retention period (e.g. 12 months for audit, account
lifetime for progress), a management command to purge expired audit rows, and a
"download my data" admin action.

### M7 — Progress can be forged (Medium)

`progress_report` clamps each request to 60 s but has no rate limit, so ~70
requests in a minute mark a 70-minute video complete. That is fine while
progress is a private convenience feature — it becomes a problem the day
completion is used for certification or CME credit. Cheapest fix: store
`last_seen_at` and refuse a report that would advance more seconds than elapsed
wall-clock time since the previous report (a token bucket per (user, tutorial)).

### L1 — 500s are served as 404s (Low)

`config/urls.py` sets `handler500 = "core.views.page_not_found"`, and that view
returns `status=404`. Real failures look like missing pages in logs and in
uptime monitors. Point `handler500` at a real error template with `status=500`,
or at least log inside it.

### L2 — No password reset (Low)

`accounts/urls.py` exposes register/login/logout/pending only. A user who
forgets their password needs a staff member with admin access. Django's
`PasswordResetView` plus an email backend would close this.

### L3 — Old WordPress JS is still served (Low)

`/static/js/core.js`, `frm.min.js`, `ruleJS.lib.full.js`, `front.min.js` are the
mirrored bundles. They include an `eval` in a third-party library and a large
amount of dead code. They disappear naturally as pages are converted; until then
treat them as an untrusted surface (M2 matters more because of them).

### L4 — Thumbnails will not load in production (Low)

`config/urls.py` adds the `/media/` route only when `DEBUG=True`. On cPanel the
files are uploaded but never served. Either map `/media/tutorial_thumbs/`
explicitly through the web server, or move thumbnails to `static/` on save.

## 4. Privacy review

### Data the site holds

| Data | Where | Why |
|---|---|---|
| Username, first/last name, email, password hash | `accounts.User` | Account + approval workflow |
| Approval status, approver, timestamps | `accounts.User` | Access decisions |
| Actor, target, action, detail, **IP address**, timestamp | `accounts.AuditEvent` | Accountability for access changes |
| Seconds watched, percent, completed, last seen | `tutorials.TutorialProgress` | Learner's own progress indicator |
| Per-tutorial grants | `tutorials.TutorialAccess` | Authorization |
| Thumbnail images | `media/` | Catalog art (staff-uploaded) |
| Playback tokens | cache, 5 min | One-time authorization |

No health data, payment data or special-category data is collected. No
analytics, no advertising, no session recording in the new templates.

### Third parties that see a visitor

- **Bunny Stream** — the only party contacted during playback; receives the
  viewer's IP and user-agent, plus a signed embed token. Must appear in the
  privacy policy as a processor.
- **YouTube / Vimeo** — 10 mirrored pages (M1), currently passive.
- **No others** on converted pages: the sanitizer removes Zoho, Jazz, Bing,
  Typekit and Google Tag Manager references, and rewrites external form actions
  to the local stub.

### Cookies actually set

- `sessionid` (HttpOnly, Secure + SameSite=Lax in production) — sign-in state.
- `csrftoken` — form protection.
- Nothing else from the app. Mirrored pages may still set Divi/site cookies, and
  the embedded players set their own (M1).

### Gaps

1. No lawful-basis / purpose statement that matches the actual processing (M5).
2. No retention schedule, no purge (M6).
3. No export/erasure path (M6).
4. No cookie banner is needed *if* M1 is fixed and no other third parties load
   passively; today the mirrored pages make that statement untrue.
5. Audit IP retention should be justified in the policy (security purpose) or
   shortened.

## 5. What is already good

- Authorization is centralised and re-checked on every request; the access
  matrix is covered by tests.
- Playback is a two-stage, POST-only, CSRF-protected handshake; the signing key
  never leaves the server.
- CSRF, clickjacking (`X-Frame-Options: DENY`), MIME sniffing, referrer policy
  and COOP are all handled.
- Production settings fail closed: no `SECRET_KEY` → refuses to start, no
  `ALLOWED_HOSTS` → refuses to start, secure cookies, SSL redirect, HSTS
  switchable.
- Staff-only surfaces are gated and every mutation is audited; self-approval is
  blocked.
- Uploads are extension- and size-constrained, with no SVG.
- The sanitizer's form retargeting means no visitor data reaches a third party
  through the mirrored forms.
- 164 tests cover the access matrix, token one-time use, revocation, CSRF,
  sanitization and the production profile (155 pass; the 9 failures are design
  assertions in `core/tests.py`/`tests_phase9.py` that still expect the old
  markup, not security failures).

## 6. Suggested order of work

1. **H1** — bind the redeem token to the session (+ test). Half a day.
2. **H2** — close the pixel/`eval` gap in the sanitizer (+ a scan test over all
   legacy files). Half a day.
3. **M5** — rewrite the privacy and cookie policies for the real controller.
   Needs a decision from you, not just code.
4. **M3/M4** — per-IP throttle and `/admin/` throttling.
5. **M2** — CSP, starting permissive and tightening as legacy pages are
   converted.
6. **M1** — click-to-load for the remaining embeds.
7. **M6/M7** — retention command, export, and a progress rate limit.

## Appendix — how to re-run the two proofs

```bash
# H1: token replay (run inside `manage.py shell`)
alice = User.objects.create_user("a", password="x-Pass-123!", approval_status="approved")
TutorialAccess.objects.get_or_create(user=alice, tutorial=Tutorial.objects.filter(is_published=True).first())
c = Client(); c.force_login(alice)
token = c.post(f"/tutorials/{slug}/authorize/").json()["token"]
Client().post("/tutorials/redeem/", {"token": token}).status_code   # 200 = finding

# H2: sanitizer gap
Client().get("/benign-conditions/").content.count(b"fb_pxl_code")    # 2 = finding
```
